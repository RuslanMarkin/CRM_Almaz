# Аналитическая спецификация CP-STATUS-001

## Текущее состояние

Таблица `counterparties` не содержит статуса. Список контрагентов уже использует
общий React-компонент `StatusBadge` для визуальных меток в других разделах.
Создание и обновление проходят через `counterpartyInput` в `server/routers.ts`.

## Решение

1. Добавить в `counterparties` поле `status` типа enum с четырьмя кодами из
   бизнес-заявки; существующим записям и новым карточкам назначать `normal`.
2. Расширить Drizzle-схему, input validation и tRPC create/update.
3. Добавить словарь статусов и badge в таблицу `/counterparties`.
4. Добавить selector статуса в форму создания/редактирования и badge в карточку
   контрагента.
5. Не менять статус автоматически и не менять правила договоров в этом релизе.

## Критерии приёмки

- Существующие записи получают `normal` после миграции.
- Новый контрагент сохраняется с выбранным статусом; по умолчанию — `normal`.
- При редактировании статус изменяется и остаётся после перезагрузки.
- В таблице каждая компания показывает понятный цветной badge.
- API не принимает код вне согласованного enum.
- Существующие 28 тестов остаются зелёными; добавлены тесты новой валидации и
  server-логики.

## Допущения, требующие подтверждения бизнеса

- «Не хватает сканов» — ручная классификация, а не автоматический подсчёт
  вложений.
- «ЧС» и «Должник» в этой итерации информируют пользователя, но не блокируют
  создание договоров, спецификаций и накладных.
- Доступ к изменению статуса соответствует текущему доступу к редактированию
  контрагентов; отдельные роли будут отдельной задачей.

## Риски

- MySQL enum требует отдельной миграции и проверки на копии production-данных.
- Будущая автоматизация статуса по сканам не должна перезаписывать ручной
  статус без согласованного правила приоритета.
