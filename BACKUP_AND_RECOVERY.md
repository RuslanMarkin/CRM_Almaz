# Резервное копирование и восстановление

## Целевые параметры

* Резервная копия MySQL создаётся ежедневно в 02:00 UTC.
* RPO: до 24 часов; при включённом point-in-time recovery у MySQL-провайдера — меньше.
* Записи и сканы, удалённые из приложения, помещаются в корзину. Их можно вернуть через `/recycle-bin`; физическое удаление приложением не выполняется.

## Однократная настройка хранилища

1. Создайте **два разных закрытых bucket'а**: `logistics-doc-scans` для рабочих файлов и `company-logistics-backups` для резервных копий. Не используйте один bucket.
2. Для bucket со сканами включите versioning. Задайте lifecycle: прежние версии хранить не меньше 90 дней. При возможности включите репликацию в другой регион или независимый аккаунт.
3. Для bucket бэкапов включите versioning и срок хранения не меньше 90 дней. Учётной записи планировщика выдайте только `PutObject` на префикс `mysql/`; не выдавайте `DeleteObject`.
4. У MySQL включите автоматические ежедневные бэкапы и point-in-time recovery, если это поддерживает выбранный тариф. Это защищает период между ежедневными дампами.

## Ежедневный запуск

Скрипт [backup-mysql-to-s3.sh](ops/backup-mysql-to-s3.sh) создаёт согласованный дамп (`--single-transaction`), сжимает его и отправляет в независимый bucket по датированному пути.

На отдельном сервере, контейнере-планировщике или в CI-планировщике установите `mysqldump`, AWS CLI и Node.js, задайте переменные из [backup.env.example](ops/backup.env.example), затем добавьте cron-задачу:

```cron
0 2 * * * /absolute/path/to/logistics-docs/ops/backup-mysql-to-s3.sh >> /var/log/logistics-backup.log 2>&1
```

Не запускайте задачу в веб-контейнере Railway: его файловая система и жизненный цикл не предназначены для расписания. Используйте отдельный cron-service Railway, GitHub Actions по расписанию либо внешний сервер с доступом к MySQL и bucket.

## Проверка восстановления

Раз в квартал скачайте свежий архив в изолированную тестовую БД и проверьте, что приложение открывает договоры и сканы:

```bash
aws s3 cp s3://company-logistics-backups/mysql/YYYY/MM/DD/backup.sql.gz - | gunzip | mysql -h test-mysql-host -u restore_user -p logistics_docs_restore
```

Факт проверки, дату дампа и ответственного фиксируйте в журнале эксплуатации. Бэкап считается рабочим только после успешного тестового восстановления.
